핵심 문제 해결 스토리

현업에서 직면했던 도전적인 기술적 과제들과 이를 해결하기 위한 사고 과정,
그리고 백엔드 개발자로서 치열하게 고민한 실질적인 대응 전략을 정리했습니다.

Problem Situation

템플릿의 부모·자식 데이터를 함께 복사하면 Auto Increment로 새로운 PK가 발급됩니다. 이 때문에 자식 데이터가 기존 부모 PK를 그대로 참조하면 복사된 데이터의 계층 관계가 깨지는 문제가 있었습니다.

Action Plan

복사 전의 ID를 별도로 보관하고, 데이터 복사 후 기존 ID와 새로 발급된 ID를 매핑했습니다. 이후 자식 데이터가 참조하는 부모 ID를 매핑된 신규 부모 PK로 변경하여 복사본끼리 연결되도록 처리했습니다.

Core Result

"복사된 데이터에서도 기존 템플릿의 부모·자식 관계가 유지되도록 구현했습니다."

Problem Situation

여러 사용자가 동일한 장비를 거의 동시에 대여할 경우, 상태를 먼저 조회한 뒤 변경하는 방식에서는 두 요청 모두 대여 가능하다고 판단할 수 있었습니다.

Action Plan

대여 가능한 상태일 때만 상태가 변경되도록 UPDATE문의 조건에 현재 상태를 포함했습니다. 이후 실제 변경된 행 수를 확인하여 1건이면 대여 성공, 0건이면 다른 요청이 먼저 처리된 것으로 판단했습니다.

Core Result

"별도의 애플리케이션 락을 구현하지 않고 조건부 UPDATE와 영향 행 수 확인을 통해 동일 장비에 대한 동시 대여 요청을 처리했습니다."

Problem Situation

기존 메모 기능에 이미지, 동영상, PDF 첨부 기능을 추가하면서 파일별 썸네일 처리가 필요했습니다. 특히 아이폰에서 업로드되는 HEVC 영상은 웹 환경에서 바로 사용하기 어려웠고, 영상 변환 과정에서 원본과 임시 파일이 계속 쌓일 수 있는 문제도 있었습니다.

Action Plan

PDF는 PDFBox, 동영상은 JCodec 등을 이용해 썸네일을 생성했고, HEVC(H.265) 영상은 FFmpeg를 호출해 H.264 코덱의 MP4로 변환했습니다. 인코딩이 완료되면 원본 파일을 바로 삭제했으며, 오류 등으로 남은 임시 파일은 3시간 주기의 스케줄러로 정리했습니다.

Core Result

"이미지·영상·PDF를 하나의 메모 기능에서 처리할 수 있도록 구현하고, 영상 변환 후 원본 및 임시 파일이 서버에 계속 쌓이지 않도록 관리했습니다."

Problem Situation

안전교육 영상을 일정 시간 이상 시청했는지 관리해야 했고, 프론트 화면의 상태만으로 처리하지 않고 사용자별 시청 진행 상태를 서버에 보관할 필요가 있었습니다.

Action Plan

프론트엔드에서 시청 신호를 전달하면 서버 시간을 기준으로 시청 시점을 저장하고, 교육시간을 반영한 이수 가능 시각을 미리 계산해 저장했습니다. 이후 요청 시 서버 현재 시간과 이수 가능 시각을 비교하여 기준 시간이 지난 경우 이수 완료 상태를 반환했습니다.

Core Result

"프론트엔드의 시간값에 의존하지 않고 서버 시간을 기준으로 이수 가능 시각을 계산후 비교하여 교육 이수 여부를 처리했습니다."
